# Dynamic agent policy — design

**Date:** 2026-08-30
**Status:** approved, not yet implemented

## Why

On 2026-08-30 the airport ran reverse (east-flow) operations and the autonomous
agent went nearly idle, leaving the rig pointed at the neighbours' houses for
minutes at a time.

The agent was not broken. It was starved. Measured against the live feed, **2 of
14 trackable aircraft were eligible**:

```
hex     flight   type  rng_km  alt_m  climb  track   tier
a4ee2e  AAL645   A21N   21.9   2492   1856   275.7    3   eligible
a37da1  ENY3929  E170   34.6   3353   2240   319.0    3   eligible
a26bb8  SKW3951  E75L    5.4    785   -960    89.7   None
c0617a  POE641   E295    7.6   1120  -1664   120.1   None
ab24f1  N817SD   H25B   24.8   1768   3264    83.3   None
```

Two independent gates in `src/agent/policy.ts` exclude almost everything in east
flow:

- **Departures now head east.** Tier 3 requires `track_deg` in 190–350°.
  Eastbound departures are barred deliberately — the code says so: *"Reached by
  an EASTBOUND departure too, and that is intended."* `N817SD` climbing at 3264
  fpm is a textbook departure rejected purely on heading.
- **Arrivals descend.** `isWestboundDeparture` requires `climb_fpm >= 500`, so no
  arrival is ever eligible, in either flow direction.

The thresholds are module constants with no config override, so adapting to a
flow change requires a code edit and redeploy. This design makes the rules data.

## Non-goal, explicitly preserved

`policy.ts` exists because the small local model drifts on multi-clause
absolutes. Making rules editable must not weaken that. **The gate stays
deterministic code; only the rules it evaluates become data.** The LLM still
never sees an ineligible aircraft.

## Rule model

An ordered list. **First matching rule wins; its position is its tier.** A rule
matches when **all** its conditions pass (AND).

**Tier numbering counts only enabled rules.** Disabling a rule promotes
everything below it, so tiers are always `1..n` with no gaps. A disabled rule is
skipped entirely during evaluation and never occupies a tier.

```json
{
  "version": 1,
  "rules": [
    { "id": "large-mil", "name": "Large military", "enabled": true, "canPreempt": true,
      "conditions": [ { "predicate": "is_large_military" } ] },

    { "id": "east-arrival", "name": "East-flow arrival", "enabled": true, "canPreempt": false,
      "conditions": [
        { "field": "climb_fpm",  "op": "lte",    "value": -500 },
        { "field": "altitude_m", "op": "lte",    "value": 4500 },
        { "field": "track_deg",  "op": "within", "value": 50, "value2": 130 }
      ] }
  ]
}
```

**Fields** (all already computed by `scan_aircraft`'s `view()`): `climb_fpm`,
`altitude_m`, `track_deg`, `range_km`, `elevation_deg`, `ground_speed_kt`,
`est_track_sec` numeric; `category`, `type` via `in`.

**Predicates:** `is_military`, `is_large_military` — these stay in tested code.
The operator-string match is a word-boundary regex that exists specifically so
`"ARMYTAGE HOLDINGS LLC"` is not flagged as ARMY, and `test/agent-policy.test.ts`
pins it. A generic `contains` operator would reintroduce that false positive.

**Operators:** `gte`, `lte`, `within`, `not_within`, `in`. All bounds are
**inclusive**. `within`/`not_within` take `value` (low) and `value2` (high); on
`track_deg` they are wrap-aware, so `within 340..020` spans north. `in` compares
`type` and `category` **case-insensitively, trimmed and upper-cased**, matching
the existing `typeOf()` helper.

**Rule `id`** is generated by the UI when a rule is created (short random slug)
and never reused or renamed thereafter, so reordering and renaming stay
non-destructive. `name` is free text and purely for display.

### Three details that carry weight

**Angle wrap.** `track_deg within 340..020` must span north. Reuse `inArc` from
`track/sector.ts` rather than write a second wrap-aware comparison.

**Null never passes.** The current code is deliberate: *"Every clause is written
so a null fails the test rather than passing it."* `climb_fpm` is absent on
roughly a quarter of the feed. The evaluator enforces this once, centrally, so a
new rule cannot reintroduce the bug.

**Disabled is not deleted.** `enabled: false` keeps a rule in the list, greyed.
Flipping between west-flow and east-flow rules is two clicks, not retyping. This
is what makes the feature answer the reverse-ops problem.

### Deliberately excluded

**OR-groups.** Every current rule is pure AND, and "military OR big-and-distant"
is already two rules. Boolean nesting doubles the UI and the evaluator for no
case in evidence.

**Undo/history.** The rules are a handful of visible numbers; the store write is
atomic. Versioning is complexity without a case yet.

## Placement

The agent is a **separate process** (`dist/agent/agent.js`, MCP at
`127.0.0.1:8770`). Today the tier filter runs inside it, so the daemon — which
owns every other store and serves the dashboard — cannot say what is eligible.
Answering the question on 2026-08-30 required re-implementing `classifyTier` in
Python against the raw feed.

**Decision: evaluate in the daemon, agent consumes.**

Rejected alternatives:

- *Agent fetches the ruleset each tick.* Least churn, but the evaluator still
  lives only in the agent, so the dashboard cannot explain eligibility without
  duplicating it. Duplicated policy logic is exactly how the scan-vs-tracker
  limits mismatch (`d04d0e6`) happened.
- *Both processes read `policy.json`.* Two readers, independent caches, no reload
  story — the same shape as the stale-`R_s` fossil (`5c162bf`): two copies of one
  truth, drifting silently.

### New module `src/policy/`

- `policy/predicates.ts` — `isMilitary`, `isLargeMilitary`, ICAO type lists,
  moved from `src/agent/policy.ts`. The daemon importing from `src/agent/` would
  be backwards layering. Tests move with it:
  `test/agent-policy.test.ts` → `test/policy-predicates.test.ts`.
- `policy/rules.ts` — pure evaluator.
  `evaluate(target, ruleset) → { tier, ruleId, ruleName, canPreempt } | null`.
  No I/O, no config.
- `src/policy-store.ts` — persistence, shaped like `FloorStore`.

### `scan_aircraft` changes (additive)

- Every row gains `tier`, `rule`, `eligible`.
- New `only_eligible` param, **default `false`**. It is applied *after* the
  existing trackability filter and, like `only_trackable`, requires a solved
  orientation — an aircraft that is policy-eligible but unreachable is still
  excluded. The agent passes both `only_trackable: true` and
  `only_eligible: true`.

Default-false keeps every existing caller unaffected. The dashboard passes
`false` and renders a tier column; the agent passes `true` and gets its
candidate list. One evaluator, one implementation.

Per-condition detail is **not** in the default response — the agent's LLM prompt
is ~317 tokens and should stay lean. An opt-in `explain: true` flag can be added
later if the tier column proves insufficient.

### Agent changes

`loop.ts` loses its local `classifyTier` map and sort; rows arrive tiered and
ordered. `decide.ts` reads `canPreempt` off the chosen row instead of testing
`tier === 1`.

The invariant in `loop.ts` — *"Policy gate BEFORE the model sees anything"* —
remains true. The gate is still deterministic and still upstream of the LLM; it
executes one process earlier.

## Preemption

Today `canPreempt` is hard-coded to tier 1. With user-ordered rules, position is
the wrong anchor — dragging a row would silently change interrupt behaviour.

**Each rule carries its own `canPreempt` flag, default `false`.** `Large
military` ships with it `true`, matching today. The existing 25 s min-dwell still
applies to every switch.

## Persistence and defaults

`~/.tb3-mcp/policy.json`. Zod schema, atomic tmp+rename, read fresh per call via
`() => policyStore.get()` so edits take effect on the next agent tick without a
restart — the same contract as `sectorStore` and `rangeStore`.

### Deliberate divergence from the sibling stores

`FloorStore` and `SectorStore` both fall back to **disabled** on a missing or
corrupt file. Disabled is the safe direction for a *restriction*.

Policy inverts this. A "disabled" policy admits **everything**, the opposite of
safe, since the point of `policy.ts` is that operator absolutes are not
droppable.

> **Missing or corrupt `policy.json` → the shipped built-in defaults.** Never
> "no filtering".

The shipped defaults reproduce today's four tiers exactly, so first boot and
corruption both land on current behaviour.

**An empty rule list is legal** and means "track nothing" — a real state (pausing
autonomous selection without stopping the service). The UI states it plainly
rather than looking broken, since "the agent tracks nothing" is the symptom that
opened this work.

### Narrowing invariant

Rules only ever *narrow* the candidate set. They cannot widen past gates that
already exist: taught travel limits, sun guard, azimuth sector, elevation floor,
slew rate, telemetry freshness. Those run independently, downstream, unchanged.

No rule writable in the UI can aim the rig at the sun or past a taught limit.
This gets a test, not a comment.

## UI

New `dashboard/public/policy.js`, wired into the drawer as `sector.js` already
is, POSTing a debounced whole-ruleset save to `/api/control/policy/set`. Vanilla
JS, no build step, no new dependencies.

**Rule list** — name, on/off, tier number, edit, delete, `+ Add rule`.

Reordering uses **▲▼ buttons, not drag**. HTML5 drag is unreliable under touch
and this is a cockpit UI used on a roof.

**Rule editor** — name, `can interrupt a pass` checkbox, condition rows
(field/predicate → operator → value). Save is blocked while a condition is
incomplete, so a half-typed rule cannot reach the store.

**Live match count** — each rule shows how many currently-visible aircraft it
admits:

```
3  Westbound departure   [on ]  2 of 14   [edit]
5  East-flow arrival     [on ]  9 of 14   [edit]
```

Edit a threshold, watch the count move. This turns "why isn't it tracking" into a
question the screen answers; on 2026-08-30 it cost a Python script and a raw-feed
dump.

The aircraft list gains a **tier column** showing the matching rule name, or `—`.

## Park on idle, and the floor

### The two parks want opposite directions

`parkTiltDeg` defaults to **−20°** — the sun guard parks the lens *down*, away
from the sun. The neighbour park needs *up*, ~45°. Down is where their windows
are.

They share the machinery (`SunSupervisor`'s waypoint plan, retry escalation,
generation counter, taught-limit awareness), not the posture:

- `parkTiltDeg: -20` — sun guard, unchanged, safety-critical
- `idleParkTiltDeg: 45` — new, autonomous mode with nothing to track

**Precedence:** E-STOP latched → never park. Sun-locked → sun park wins, always.
Tracking → no park. Only a genuinely idle autonomous rig parks up.

Idle park must **not** live inside `session.stop()`. That method is on the E-STOP
and sun-lock paths, and "stop moving" must never become "now execute a slew." It
is a distinct action issued when a pass ends with no eligible candidate, guarded
by a dwell so a 5 s decision loop cannot re-issue it.

### Floor — DO NOT ENABLE YET (corrected 2026-08-30 after final review)

The original plan here was configuration only: `floor.json`
`{ enabled: true, minElevationDeg: 3 }`. **That is wrong as the code stands, and
enabling it would reproduce the exact symptom this work exists to fix.**

`isTrackable` (`src/adsb-tools.ts`) gates on
`reachable && sunSafe && slewOk && inSector` plus position age — **the floor is
not in it**. So `scan_aircraft` offers an aircraft below the floor, the agent
selects it, and only then does `TrackingSession` refuse it with
`wait("below_min_elevation")`, leaving the session ACTIVE (`waiting`, not
`stopped`). From there:

- `get_tracked_aircraft` returns the hex, so `currentHex` is non-null
- `currentHealthy` is true, because the scan has no floor and the hex is in it
- `runOnce`'s park condition requires `currentHex === null`, so **idle park
  never fires**
- `decideAction` holds a "healthy" target, so the agent stays latched until the
  aircraft leaves the feed

Net: the rig freezes wherever the last pass ended, with the fix meant to prevent
that suppressed. With 12 of 20 trackable aircraft below 3°, this is the common
case, not a corner. It is the same scan-vs-tracker divergence as `d04d0e6`.

**The floor ships separately, after `isTrackable` learns about it** — thread a
`floorProvider` into `registerAdsbTools`/`isTrackable` so scan and session judge
the same envelope, exactly as `limitsProvider` already does for taught limits.

Note this also means the narrowing invariant above ("no rule can produce a
target below the elevation floor") is currently true only because the floor is
disabled.

3° is a deliberate trade. Measured against live traffic, 12 of 20 trackable
aircraft sit below 3° and a 10° floor keeps just one. The reported problem was
*idle* dwell, which park-on-idle addresses directly without costing passes; the
floor is the smaller, adjustable second layer.

### Noted, not in scope

Taught `tiltMin` is **−2.33°** while `parkTiltDeg` is **−20°** — the sun guard's
park destination sits below the taught floor. The code anticipates this
(*"a taught limit tighter than parkTiltDeg's config default could still grind the
sun-guard's own park move into a hard stop"*), so it is defended, but the
effective sun-park posture is not −20°. Worth verifying separately.

## Testing

**Evaluator (pure):** AND semantics, first-match-wins, null never passes, angle
wrap across north, set membership, disabled rules skipped, empty ruleset yields
nothing.

**Store:** round-trip; corrupt file falls back to shipped defaults, *not* to
"admit everything".

**Migration proof:** port `test/agent-policy.test.ts` cases through the new
evaluator loaded with shipped defaults and assert identical tier results. This
makes "behaviourally a no-op until you edit something" a checked claim.

**Narrowing invariant:** a rule admitting everything still cannot produce a
candidate violating reachability, sun cone, sector, or floor.

**Agent:** `canPreempt` sourced from the row; `only_eligible` filtering.

**Park:** not on E-STOP, not on sun lock, not while tracking; dwell prevents
re-issue.

**UI:** `policy.js` exposes its logic — validation, serialization, rule→JSON
mapping — as pure exported functions with tests, keeping DOM wiring thin.
`stick-hold.js` and `aircraft-select.js` already follow this shape. Rationale:
the `tilt_dps` ReferenceError (`90a7ae6`) shipped because `app.js` had no test
and the smoke script never drove a stick drag. This will not catch a bad event
binding, but it catches the class of bug that actually bit us.
